\chapter{Executable Examples in serQ}\label{app:serq}

The examples accompanying these notes are programs in serQ v0.1.0 (IR version 9,
commit \texttt{f9fe9f2}). A serQ program declares memory pools, service stages, a
workload and a server block. Running it simulates the deployment; it does not measure
a real serving system. Each stage kind is one of the queues of the notes.

\end{center}
For example, \texttt{stage decode : ps(min(present, 16));} is a batch whose capacity
grows with the number \texttt{present} of turns up to $16$. A step stage schedules
tokens per iteration with a \texttt{budget}, a \texttt{cost} and a \texttt{serve} order;
a FIFO prefill order must be chosen there, since chunking alone does not give it.

The programs follow engine rules that the analytical models leave out. The
executable \texttt{transfer} reserves the destination before it releases the source,
unlike \cref{L6:def:path}. Allocations round up to whole blocks and cached prefixes round
down, so a partial hit has its own work law (\cref{L5:rem:partial}). A preempted decode
keeps its generated tokens and re-prefills only lost KV. Ending a session does not
remove its cached blocks.

\section{What to run and what it checks}

\texttt{programs/lecture\_pd.sq} implements \cref{L6:def:path};
\texttt{programs/vllm.sq} implements a step engine with vLLM's rules. From the
repository root, \texttt{make lecture-results} runs the course checks, which compare
simulations with Pollaczek--Khinchine, PS insensitivity, mean value analysis, the
disaggregated bottlenecks, the equilibria of \cref{L6:ex:bistable}, and the price
bracket on a step engine. Passing checks support the formulas in their stated models;
they do not make a program a proved queue.
